DOM PRIMITIVE ENGINE · V9

The Story Behind Table Extraction

From a button click to a JavaScript object: understanding the responsibilities, instructions, and decisions that make the extraction reusable.

The central question

How can an application extract data from a table without writing separate, hardcoded DOM traversal logic for every table?

The idea is to describe the extraction steps as instructions and let the engine execute them. The application supplies the starting element; the instructions describe the journey; the result is ordinary data.

1. See the complete journey

Button click→ Starting element→ Find row→ Collect cells→ Map values→ Object

Each stage has one responsibility. The output of one operation becomes the input to the next operation.

2. Start with a real table

Item Category Price Action
Keyboard Accessories 35 Extract button
Mouse Accessories 20 Extract button

Imagine the user clicks Extract in the Keyboard row. We want only the Keyboard data. If they click Extract in the Mouse row, the same extraction definition should return Mouse data instead.

3. Follow the data through each stage

STAGE 1 · INPUT

Receive the starting element

The application handles the click event and supplies the appropriate starting DOM element to the pipeline. 

Starting value: clicked button

The event handler belongs to the application. It should not be confused with the engine's job of traversing and reading the DOM.

STAGE 2 · LOCATE

Find the containing row

closest("tr")

Input: the clicked button.

Action: find the nearest ancestor-or-self matching the selector.

Output: the row containing that button.

The selected row is determined by the starting element, not by a hardcoded row number.

STAGE 3 · COLLECT

Collect the relevant cells

queryAll("td:not(:last-child)")

Input: the selected row.

Action: find its data cells, excluding the final action cell.

Output: an ordered collection of three cells.

This selector assumes the action cell is always the last cell. If the table structure changes, the selector may need to change too.

STAGE 4 · TRANSFORM

Turn the collection into an object

{
  "columns": ["itemName", "category", "price"],
  "read": "text"
}

Input: the ordered collection of cells.

Action: read each cell and pair its value with a configured key.

Output: an object with meaningful property names.

The mapping is positional: the first cell corresponds to the first key, the second cell to the second key, and so on.

The final result

{
  "itemName": "Keyboard",
  "category": "Accessories",
  "price": "35"
}

The output no longer depends on the DOM. Application code can pass the object to another function, serialize it as JSON, or send it to an API.

4. What does the instruction contract mean?

An instruction is a description of one operation. It tells the engine what operation to perform and what information that operation needs. 

[
  {
    "op": "closest",
    "args": {
      "selector": "tr"
    }
  },
  {
    "op": "queryAll",
    "args": {
      "selector": "td:not(:last-child)"
    }
  },
  {
    "op": "toObject",
    "args": {
      "columns": ["itemName", "category", "price"],
      "read": "text"
    }
  }
]
Term Meaning Example
op The operation the engine should execute. closest
args The settings required by that operation. selector: "tr"
selector A CSS rule used to locate elements. td:not(:last-child)
columns The ordered object keys for the collected values. ["itemName", "category", "price"]
read The requested way to read values. text
An important design decision

We should decide whether the public contract uses short names such as op and args, or explicit names such as operation and arguments.

The longer names may be easier to understand in documentation and configuration files. However, the implementation, samples, and tests must all use the same contract. This is a design decision to settle, not a change to make silently in documentation.

5. Why have a pipeline?

Without a pipeline, an application might write the entire extraction directly in its click handler: 

const row = button.closest("tr");
const cells = row.querySelectorAll("td:not(:last-child)");

const item = {
  itemName: cells[0].textContent.trim(),
  category: cells[1].textContent.trim(),
  price: cells[2].textContent.trim()
};

That code is understandable for one table. But if several tables and forms need similar extraction, applications may repeat the same traversal and conversion logic.

With an instruction-driven engine, the application can reuse the execution mechanism and supply a different instruction sequence for a different structure.

The engine does not eliminate the need to describe the DOM.

It moves that description into an explicit contract so the application logic and the extraction rules can be managed separately.

6. Keep the responsibilities separate

Component Its responsibility What it should not secretly decide
Application event handler Respond to the click and choose the starting element. How every field is extracted.
Instruction definition Describe the operations and their arguments. Execute DOM operations by itself.
Pipeline Execute operations in order and pass results forward. Invent application-specific field mappings.
Primitive operation Perform a defined lookup or transformation. Know the business meaning of every table column.
Application consumer Use the resulting object. Depend on the DOM traversal details unnecessarily.

7. What can go wrong?

Situation Why it matters Expected design response
No matching row The starting element may not belong to a table row. Fail clearly rather than returning misleading data.
Unexpected number of cells The table may have changed. Define whether to reject the data or handle missing values.
Column order changes Positional mapping can assign values to the wrong keys. Keep the mapping aligned with the table structure or use explicit field selectors.
Cell contains an input Displayed text and entered value are different things. Choose the appropriate read mode and define its behavior.
Unknown operation The instruction may contain a typo or unsupported operation. Report the invalid operation clearly.

8. The same idea can serve other structures

Table

Start from a clicked row action, locate the row, collect cells, and map values to an object.

Form

Start from a form, collect relevant controls, read their values, and map them to an object.

Other DOM structures

Reuse the same execution model when the required operations are supported. A new structure may need different selectors or a different mapping.

Reuse does not mean every DOM structure needs the same instructions. It means the engine can execute different descriptions through a consistent mechanism.

9. The design we want to preserve

  1. The application supplies the starting element.
  2. The instructions describe the extraction journey.
  3. The pipeline executes each operation in order.
  4. Each operation has a clear responsibility.
  5. The final result is application-friendly data.

If we keep these boundaries clear, future improvements to the instruction vocabulary or the primitive operations become easier to reason about.
